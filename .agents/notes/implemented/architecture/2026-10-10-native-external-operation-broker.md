# Agent Note: Native external-operation broker

Status: implemented

English | [中文](2026-10-10-native-external-operation-broker.zh.md)

## Problem

An external product can make model-visible requests and receive responses outside the Native Session loop. Parent start/end facts alone cannot reconstruct those requests or outcomes, and logical child steps do not bound provider retries.

## Decision

The detached external-driver request carries a narrow model-operation capability owned by `NativeSpawnSubagents`. The Engine admits model requests only for the captured active parent and invocation-root owners and resolved route. It reserves each outbound attempt synchronously before awaiting the flushed `subagent/external-start` fact; retries consume additional reservations, and the operation cannot reserve more than `maxSteps`. Exceeding the ceiling latches a fatal error, cancels the existing operation, drains its child range and attempts, and records an error end without publishing a successful result.

Each admitted attempt records the complete parsed Responses request before forwarding. Its complete parsed SSE event sequence, terminal response or failure, and exact response-derived tool-call projection are recorded through the captured parent writer before the product exposes or retries the outcome. A response received after cancellation or owner replacement remains a recorded fact but is rejected before delivery. Failure settlement uses the captured writer and always releases the lease; writer failure remains a sticky drain failure. Lease identity is bound to one operation and can be settled once.

The same captured `NativeExternalToolOperations` snapshot supplies direct schemas, program schemas, prompt text, tool execution and deferred Native acceptance. The Engine creates one-use grants only for the parsed calls recorded on that response, writes `tool-call` and the complete `tool-result`, then accepts the captured result and writes `tool-settlement` with settlement contexts and `concludesTurn`. After settlement persistence, the captured Headless attachment service resolves only image references in that accepted result and its settlement contexts to verified bytes; capture disposal drains these reads. The Engine rejects another inference while an attempt or any call from the previous response is unsettled, and rejects all later inference after a settlement concludes the turn. A rejected early inference does not cancel the accepted calls in that batch. On normal completion the child range and accepted tool pipelines drain before captured-tool disposal; cancellation disposes the capture to stop bodies, then drains tool settlements.

Headless permits only the `tool/ptc-dispatch` settlement append after cancellation, preserving the required error outcome for each started PTC call while keeping PTC starts and other event writes abort-guarded.

The Official Responses driver consumes a borrowed transport captured from the exact prepared model call selected by the Engine. A matching route reuses that generation; an explicit route change prepares its selected provider and model once. The Engine closes the transport after product disposal and accepted model, tool and approval work drain. A parent `maxTokens` ceiling requires the captured generation to enforce it, and the gateway checks the final projected `max_output_tokens`; unsupported or missing capability rejects before child startup. Nested Responses calls inherit a process-local capability bound to the exact outer prepared generation. A matching route captures an independent transport from that generation; an explicit provider/model change prepares one child generation without changing its parent. Each child owns its transport, and the Engine closes it after product disposal and accepted work drain.

The serializer only encodes a JSON value. The product adapter parses and filters the wire request first and keeps headers, credentials, environment and upstream URLs out of the event. The Engine gives the adapter no Agent, Session, Context or writer.

## Alternatives considered

**Give the product adapter Native owners or the Session writer.** That would let the adapter append model history directly, but it would transfer Program-owned identity and persistence authority across the product boundary. The Engine instead exposes operation-scoped callbacks and writes events through the captured owner.

**Use logical child steps as the request ceiling.** A product can retry inside one logical step, so that count would not cap outbound attempts. The Engine counts each attempt, including retries, against `maxSteps`.

## Consequences

`subagent/external-operation` is a required-on-read Session event. Its variants retain `model-request` route and request body; `model-response` SSE events, completed response and exact `toolCalls`; `model-failure`; `tool-call` name and arguments; `tool-result`; and `tool-settlement` contexts and turn conclusion. The standard persistence catalog includes it without changing the Session envelope version or rewriting committed Session generations. The keyless snapshot identity mapper normalizes `parentEpoch` and `rootEpoch` on `subagent/external-start` and `subagent/external-operation` to stable first-seen epoch tokens, preserving repeated-identity relationships. The keyless snapshot normalizer also zeros only numeric top-level clock values: `data.startedAt` on `subagent/external-start`, `data.at` on the six `subagent/external-operation` variants, and `data.finishedAt` on `subagent/external-end`; nested same-named clock fields remain unchanged. The Official Native Codex driver consumes the Engine-captured prepared-generation transport; the shipped SIWC `openai-codex` provider supplies it when selected. Shipped profile templates keep in-process `spawn` and omit the Codex driver, whose external background mode remains unsupported. The SIWC transport does not enforce output-token ceilings. Codex product execution and TypeScript and Python SDK event projections remain unverified release dependencies; the scripted scenario below does not establish them or P4 acceptance.

The Host dependency policy classifies only `JsonRpcLineTransport`, whose mutable state belongs to each transport instance, and `disposeChildConnection`, whose state belongs to each call. It does not classify `JsonRpcResponseError`; `instanceof` checks against that class are not guaranteed across package copies.

Registry disposal waits for every owner release to settle before it reports collected cleanup failures. One failed cleanup cannot end disposal while another owner still drains.

The policy also marks the Codex app-server's `ToolCallId`, `fileHandleText`, and `serializeNativeExternalJson` imports as peer-required Host exports; the consumer dependency requirement is documented in the [Codex app-server README](../../../../rsh/Modules/Official/subagent/codex-app-server/README.md).

The focused `external-driver.spec.ts` case verifies that first admission waits for the start flush, request and response events are persisted, the attempt ceiling aborts, and drain precedes the error end. Its nested Responses case uses `NativeModelExecution` to verify same-route generation retention, one preparation for a changed route, and preservation of the parent generation. The `external-tools.spec.ts` Responses case verifies the prepared generation remains captured after model selection changes, close rejects new work and waits for an accepted response body and provider cleanup, and close revokes its nested capture factory. A Native Headless regression executes real PTC `run_code` → `tool-subagent` → nested Responses work, aborts the parent after the nested forward is accepted, then cold-reads the paired PTC start and error settlement and verifies product disposal precedes transport close. A shipped-CLI snapshot also triggers cancellation from its parent with POSIX SIGTERM and SIGINT after nested-forward readiness; Windows keeps an in-process SIGTERM handler trigger. Neither branch verifies console Ctrl-C delivery. The adapter and external driver are scripted test fakes; ordinary-turn appender symmetry is source-reviewed, and neither test establishes a real Provider Responses implementation. The two-call tool case holds the first body, rejects premature next inference without cancelling either accepted call, verifies each durable result precedes Native acceptance and settlement, and verifies `concludesTurn` blocks later inference before a normal completed child ends. The focused dsh broker scenario uses a mock model and scripted external driver: the first attempt fails, a retry performs a real filesystem write, the result and durable settlement with empty `settlementContexts` are recorded, and the next inference proceeds. Cold JSONL replay is checked against the complete workspace oracle. The scenario does not exercise non-empty settlement contexts or cancellation.
