# Agent Note: Standard profile names create Native profiles

Status: implemented

English | [中文](2026-10-17-standard-native-profile-defaults.zh.md)

## Problem

The ordinary profile names and the shipped `native-*` names select parallel implementations of the same CLI surfaces. Requiring users to know the runtime-specific names leaves Native as an opt-in despite the installed native dependency closure.

## Decision

When no profile manifest exists, `headless`, `web`, `sdk`, `acp`, and `rsh` create the `native-headless`, `native-web`, `native-sdk`, `native-acp`, and `native-tui` compositions under the requested profile names. The existing eight `native-*` aliases remain available, and `sdk-minimal` remains a legacy bundle profile.

An existing `package.json` remains the authority for runtime selection. Native initialization returns without changing it; `profileRuntime` selects Native from the explicit Native marker and legacy from the legacy marker or bundle list. Native Web project data and the scheduler database use the actual profile directory name.

The TypeScript and Python SDKs continue to default to `sdk`. The TypeScript source launcher resolves the installed or built `dsh` entry without a Cordis profile overlay; callers that need a legacy SDK composition create a custom profile from the explicit `sdk` bundle template.

## Alternatives considered

**Rewrite existing profiles when their names become standard Native names.** Rejected because a standard name can already own a user-managed legacy profile and its dependencies, patches, settings, and data.

**Change SDK defaults to `native-sdk`.** Rejected because `sdk` is already the public SDK profile and the new default mapping can select Native without changing the SDK option.

**Create more aliases or infer a runtime from remaining files.** Rejected because the manifest already provides an explicit resolver and the existing `native-*` aliases cover runtime-specific selection.

## Consequences

New standard profiles use Native configuration and plugin management rejects their package-management command with directions to edit `rsh.profile.json` installations. Existing legacy manifests continue through Cordis. A new legacy app composition requires a custom profile name and `--from-default-profile`; `sdk-minimal` keeps its independent legacy runtime.

Focused CLI, package, and packed-consumer checks cover the mapping, profile preservation, Native paths and refusals, Cordis-free headless launch, and installed SDK declarations. The installed declaration check uses strict NodeNext resolution with consumer-owned Node types and ESNext disposable declarations.

Fresh Desktop profiles, exact Desktop starter conversions, resets, and development profiles select the single encoding found among canonical live generations and retained deletion payloads under the shared Session root; empty roots use `none`, and mixed or obsolete flat live data are rejected before profile writes or Host stop. Existing Native Desktop profiles keep their configured encoding during ordinary upgrades.

Desktop imports this preflight from the JSONL package's `./native-inspection` entry, which does not load the persistence backend.

The profile composer reads shipped profile names from the CLI package manifest through its exported `./package.json` entry, keeping the CLI manifest as the only template-name source when Desktop bundles the composer.

The LLM root and Native entries export message constructors and message-only types directly; shared message types, including `MessageSourceMap`, flow through `types.ts` once so generated declarations have one unambiguous source.

Session expected files remain authored data and are not regenerated by this default change.
