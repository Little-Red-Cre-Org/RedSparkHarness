# Agent Note: Native compatibility bridge

Status: implemented

English | [中文](2026-09-22-native-compatibility-bridge.zh.md)

## Problem

The native filesystem and headless profile need selected legacy filesystem implementations during the staged migration, but starting a legacy bundle would introduce competing Agent, tool, and Session writers.

## Decision

The optional `compat-dsh-runtime` creates one Cordis Context and exposes it only to the selected compatibility bridges through the `compatDshRuntime` service. The bridges mount allowlisted plugins through `dsh-plugin-host`, which owns child Fibers and descriptor registrations. `compat-fs-local` and `compat-fs-sandbox` each provide `fs`; the sandbox variant requires native policy selection. `compat-fs-policy` forwards native filesystem events into the legacy observation policy and provides the policy authority marker. `compat-tool-fs` registers selected legacy tools and prompt sections into native registries, while the native headless application validates calls and appends exactly one Session result.

Each bridge validates its selected package metadata and configuration before mounting a Loader entry in the shared Cordis Context. The runtime checks exact Cordis 4.0.2 and Loader 1.0.3 releases, plus the supported DSH package declarations, before activation. Native tools and prompt sections drain admitted tool calls and in-flight prompt assembly before Loader updates; policy listeners drain before their entry changes. Bridge disposal removes owned Native contributions, and Host shutdown drains the Context. Native installations that omit `compat-dsh-runtime` do not load Cordis through this compatibility path. The compatibility profile exercises the published `dsh` command with a legacy write tool, filesystem change, model-visible prompt and schema, and one durable result. [The Loader entry lifecycle decision](2026-10-06-native-compatibility-loader-entry-lifecycle.md) owns the support matrix and reload distinction.

## Alternatives considered

**Load the legacy base bundle.** It was rejected because it owns an Agent loop, Session state, and tool runtime that conflict with native authorities.

**Rewrite the selected legacy packages immediately.** It was rejected because the staged migration needs behavior evidence from the maintained filesystem implementations before their replacement phases.

**Allow a sandbox bridge to select local storage when policy is absent.** It was rejected because a missing policy must fail loudly instead of widening mutation access.

## Consequences

Native profiles can consume selected legacy filesystem implementations without a second durable Session writer. The compatibility layer remains bounded to the declared packages and retains Cordis as an explicit dependency. The native policy has profile-level modes only, and broader approval, attachment, UI presentation, reload, and replacement behavior remain owned by later migration phases.

## Testing

The bridged filesystem events are `fs/observed` (sync) and the `fs/write-intent` and `fs/edit-intent` waterfalls. These are every event the Native and Cordis filesystem domains declare or dispatch; neither declares a parallel or serial filesystem event, so the bridge has no such mode to adapt. The `compat-tool-fs` waterfall case compares Native-originated and Cordis-originated dispatch for listener order, `next()` delegation through both sides to the caller's terminal, throws, short-circuit, and async rejection; counted terminals prove that short-circuit and rejection never invoke the caller's terminal. The `compat-fs-policy` case covers Native-to-Cordis forwarding into the observation policy, which terminates the waterfall by design rather than delegating to later Native listeners. The `compat-fs-local` case runs the production Native `read` and `write` tools against the Cordis fs-local Provider and replaces that Provider with a fresh instance using a different `cwd`. It asserts that replacement aborts a write admitted on the old backend with `FS_ABORTED`, that no `fs` service is published when the old backend's cleanup begins, that the old write's staging directory and temporary file exist while that cleanup is held and are already deleted when the substitute `fs` service is first published, that the cleanup completes before the replacement settles and the substitute then serves the next read, that the retained old instance refuses new I/O, and that removal leaves the live proxy reporting the service as unavailable.

The bridge allowlist pins the four filesystem packages (`dsh-fs-local`, `dsh-fs-observation-policy`, `dsh-fs-sandbox`, `dsh-tool-fs`), `dsh-tools`, and `dsh-system-prompt`, plus the internal `sandbox-policy-adapter`, `fs-adapter`, and `fs-event-bridge` adapters. Tool approval, code runtime, user questions, and automation have no Native bridge (`compat-user-approval` and `compat-code-runtime` are Cordis-internal plugins), so their event semantics are verified on the Native side only; a Native-to-Cordis comparison becomes applicable only if one of them joins the allowlist. Provider replacement for these families runs in a live Native Host through `NativeHost.replace` with the production Consumer unchanged. The native-headless PTC case runs `run_code` on the real worker-thread runtime, holds the old runtime's cleanup to show that the replacement neither settles nor activates the substitute before it, and then asserts the model-visible results `42` from the real runtime and `7` from the controlled substitute by tool-call ID. The `tool-ask-user` case first removes the delegating answerer while a question is pending, which cancels the broker presentation and persists `ASK_ABORTED`; it then replaces the real question broker with a controlled broker while another question is pending, holds the old broker's cleanup in the same way, observes the old broker already disposed when the substitute activates, and has the substitute answer the next question.

`dsh-tools` and `dsh-system-prompt` are mounted only as `compat-tool-fs` support services, so Tools and prompt assembly cross the bridge as services rather than as bridged events. A Cordis tool reaches Native callers through the Native `execute` service; the Cordis `pre-execute`, `execute`, and `post-execute` waterfalls and the Native `aroundExecution` and `postResult` waterfalls each stay on their own side. The `compat-tool-fs` case therefore compares the content, error flag, and error message of the same read through both services for a successful read and a missing file. Native `promptSections` render the output of Cordis `systemPrompt.assemble()`. The case compares Native `prompt.render()` with Cordis `assemble()` for the full prompt text and `system-prompt/assemble` waterfall order, short-circuit, a synchronous throw, and an asynchronous rejection that both sides surface as the same error object. `system-prompt/change` is not forwarded, and compaction is not in the allowlist, so compaction events are verified on the Native side only until compaction joins the allowlist.

Within Native, the `native-tools` lifecycle spec registers a same-name tool in two sibling Agent scopes and runs one queued call and one delegated call concurrently; each call keeps its own initiator, Agent, Session, parent, and delegation context. The native-headless delegation case runs the production Headless Consumer against a same-name tool in a child Agent scope and checks the child call ID, Session, initiator, SessionExecution authority, and tool authorization.

Two more native-headless cases replace a Provider while the Headless application keeps running. The Tools case replaces the real Tools Provider with a substitute registry: the in-flight call is aborted and the run rejects, the old registry's cleanup is held to show that the replacement neither settles nor activates the substitute before it, the old registry is already cleared and disposed when the substitute activates, an `execute` reference captured before replacement rejects without running the old tool or the substitute, and the model-visible results are compared by tool-call ID. The Skill case first reads a real local `SKILL.md` through `skill-filesystem` and the production ToolSkill Consumer, then replaces that Provider with a controlled one. It holds the old Provider's read and cleanup, settles the in-flight ToolSkill call as an unavailable skill, observes the old resources released when the substitute activates, and compares both turns' full model requests and persisted tool results, allowing only message, call, and Session IDs, the abort signal, and the two Providers' Skill content to differ. Removing the wait on held cleanup makes both cases fail.
