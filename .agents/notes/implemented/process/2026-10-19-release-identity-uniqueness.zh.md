# Agent Note: 一个包身份只发布一份载荷

Status: implemented

[English](2026-10-19-release-identity-uniqueness.md) | 中文

## Problem

npm 包身份由名称加版本构成，npm 无法在同一身份下容纳第二份载荷。`@deepseek-ai/dsh-tool-fs@0.1.5-rc.2` 只指向一个 tarball；第二个要么覆盖第一个，要么发布失败，而已经拿到第一个的消费方无从索取另一个。因此发布必须在上传任何东西之前证明：没有包身份被认领两次，且同一个身份从不携带两个版本。

`releaseFamily().members()` 在发现某个家族的待发布清单时已经强制了这两半：当第二个目录认领同一名称时抛出 `<name> appears twice in release family <id>`；`verifyVersions` 在成员版本不一致时抛出。但**没有任何测试演练过这两条规则**。一个只有守卫在防的发布缺陷、却没有测试证明守卫会触发，等于把一个保证寄托在没人刻意跑过的代码上。

## Decision

一个包身份只携带一份载荷，打包路径在两个点上强制它。

`releaseFamily().members()` 继续拒绝跨家族的重名，因此两个目录永远无法把同一个身份贡献进一次发布集。`verifyVersions()` 继续要求同一家族只有一个版本，因此一个 tag 就足以命名整套。

`families.spec.ts` 现在证明两条规则都会触发。每个用例只构建该规则需要的那几个清单到一个临时根目录，因此守卫是对着真实的家族运行的，而不是对着被 mock 的成员列表。一个把 `seen.has(name)` 检查禁掉的负向对照会让重名用例失败，这说明该测试测的是守卫本身，而不是在守卫旁边恰好通过。

打包产物集也按同一条规则核对：冻结 P6 SHA 下产出的 dsh 家族 331 个 tarball，携带 331 个互不相同的名称，全部为 `0.1.5-rc.2`，没有任何名称出现两次。

## Alternatives considered

**把打包出的 tarball 互相比较，就当作检查。** 否决：那只是检视某一次构建的产物。规则必须对下一个包也成立，所以它属于「发现将要发布什么」的那一步，而不是对「已经发布了什么」的扫描。

**因为守卫显然正确就相信它。** 否决：「显然正确」恰恰是需要一个负向测试来确认的说法。重名用例成本很低，而禁用守卫的对照证明了它测的正是那一行。

**让 registry 在发布时拒绝重复。** 否决：发布已经是最后一步——在那里才发现重复身份，意味着已经打包、已上传家族的一部分，可能留下需要手工修复的半成品发布。在发现阶段失败不花任何代价。

## Consequences

第二个认领既有包名的目录现在会在 `release:pack` 阶段失败，错误点名该名称与家族，且发生在写出任何 tarball 之前。版本不一致的家族在同一阶段失败，这保持了一个 tag 命名一次发布。

两个 spec 用例每次运行增加一个临时根目录；它们只构建自己读取的清单，因此运行很快，且不依赖仓库自身的包集合。

该检查是按家族进行的。若某个包合法地需要从两个家族发布同一个名称（例如原生版旁边的兼容构建），需要扩展规则而不是绕过它；目前不存在这样的成员，且仓库中完全没有重复的可发布身份。
