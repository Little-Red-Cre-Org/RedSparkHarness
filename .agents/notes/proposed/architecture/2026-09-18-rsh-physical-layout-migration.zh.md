# Agent Note: 运行时重构之前的 RSH 物理目录迁移

Status: proposed

[English](2026-09-18-rsh-physical-layout-migration.md) | 中文

## 问题

要求的 RSH 组织方式区分基础设施、agent（智能体）执行、功能实现、DSH 兼容和应用入口。同时移动文件并改变运行时职责，会使故障难以归因：导入路径错误可能表现得像生命周期或组合回归。目录树本身也不能证明依赖已经遵循未来的目标分层。

## 提案

先完成物理迁移。保持包标识、公开导出、Cordis 组合、基于配置方案的应用启动、Session 格式和可观察工具行为不变。在同一变更中更新路径相关消费方：工作区 manifest（元数据清单）、编译器项目、构建与发布脚本、fixture（测试前置数据）、文档、CI 和本地 Git 集成。运行时依赖倒置和替换接口属于独立阶段，不是本次移动已经证明的能力。

[包地图](../../../../rsh/README.zh.md)描述现有包职责。`Core` 包含基础设施和内置上游源码；`Engine` 包含 agent 执行与 Session 能力；`Modules/Official` 和 `Modules/Community` 包含实现与扩展；`Compatibility/DSH` 包含 DSH 组合支持；`Programs` 包含应用与 SDK 所有者。这些目录分配不会消除现有 Cordis 依赖。

源码发现使用[工作区匹配规则](../../../../rsh/Scripts/workspace-manifest-globs.ts)，并区分发布包与私有应用策略。应用根路径与包内局部路径保持区分。Python 部署依赖集合与 Desktop 打包输出属于产物，绝不是新增工作区源码包。发现未登记源码启动器的检查必须保留这项覆盖，同时排除生成的运行时文件。

## 考虑过的替代方案

**在同一变更中移动文件并替换运行时。** 这会掩盖故障究竟来自迁移还是语义变化，并违背先物理迁移的要求。

**保留重复源码树或永久旧路径转发目录。** 这会造成职责不明确，并让陈旧副本掩盖未更新的消费方。恢复副本保留为备份，不作为并行开发根目录。

**将 Programs 下所有 manifest 递归视为工作区。** 构建出的 Python 运行时包含另一份 manifest 和依赖树。该策略会在打包后改变工作区成员，并使源码检查处理分发副本。

## 验收标准

- 每个迁移后的源码包只有一个权威物理位置。包名和受支持的配置方案入口保持不变；所有受影响消费方解析到新路径，不依赖旧目录别名。
- 工作区、编译器、发布、文档与 CI 清单覆盖每个相关所有者的实际目录深度。拒绝错误路径的测试证明检查能够发现无效源码，而不仅是当前目录通过。
- 生成的 Desktop 与 Python 产物存在时，源码验证仍成功。测试同时验证产物被排除，以及相邻无效源码仍被拒绝。
- 构建、类型检查、lint、hygiene、文档检查，以及相关源码和已构建运行时测试通过。Windows 与 POSIX 结果、过滤用例、跳过用例和未执行检查按照[测试策略](../../../../rsh/Docs/testing.zh.md)分别报告。
- Desktop 与 Python 打包运行时从迁移后的输出位置启动。命令退出或归档创建成功本身不等于运行时验证。
- 原开发目录具有可读取的 Git 索引，并保留用户文件。最终交接前记录恢复备份和剩余验证缺口；迁移验收完成前，本记录保持 proposed。
