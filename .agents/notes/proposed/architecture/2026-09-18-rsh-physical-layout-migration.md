# Agent Note: RSH physical layout before runtime restructuring

Status: proposed

English | [中文](2026-09-18-rsh-physical-layout-migration.zh.md)

## Problem

The requested RSH organization separates infrastructure, agent execution, feature implementations, DSH compatibility, and application entry points. Moving files and changing runtime ownership together makes failures difficult to attribute: a broken import can look like a lifecycle or composition regression. A directory tree alone also cannot prove that dependencies follow the intended future layering.

## Proposal

Complete the physical relocation first. Preserve package identities, public exports, Cordis composition, profile-based application launch, Session formats, and observable tool behavior. Update path-dependent consumers in the same change: workspace manifests, compiler projects, build and release scripts, test fixtures, documentation, CI, and local Git integration. Runtime dependency inversion and replacement interfaces remain a separate phase, not claims established by this move.

The [package map](../../../../rsh/README.md) describes existing package ownership. `Core` contains infrastructure and vendored sources; `Engine` contains agent execution and Session capabilities; `Modules/Official` and `Modules/Community` contain implementations and extensions; `Compatibility/DSH` contains DSH composition support; `Programs` contains application and SDK owners. These directory assignments do not remove existing Cordis dependencies.

Source discovery uses the [workspace patterns](../../../../rsh/Scripts/workspace-manifest-globs.ts), with separate policies for published packages and private applications. Application-root paths and package-local paths remain distinct. Python deployment closures and Desktop packaging output are artifacts, never additional workspace source packages. Checks that discover unregistered source launchers must retain that coverage while excluding generated runtime payloads.

## Alternatives considered

**Move files and replace the runtime in one change.** This obscures whether failures come from relocation or changed semantics and contradicts the requested physical-first sequence.

**Keep duplicate source trees or permanent old-path forwarding directories.** This leaves ambiguous ownership and lets a stale copy hide missing consumer updates. Recovery copies remain backups, not parallel development roots.

**Recursively treat every manifest below Programs as a workspace.** A built Python runtime contains another manifest and dependency tree. That policy changes workspace membership after packaging and makes source checks consume distributed copies.

## Acceptance criteria

- Each migrated source package has one authoritative physical location. Package names and supported profile entry points remain intact; all affected consumers resolve the new paths without old-tree aliases.
- Workspace, compiler, release, documentation, and CI inventories cover every relevant owner at its actual depth. Rejected-path tests prove that checks detect invalid source, not merely that the current tree passes.
- Source validation succeeds with generated Desktop and Python artifacts present. Tests verify both artifact exclusion and continued rejection of invalid adjacent source.
- Build, typecheck, lint, hygiene, documentation checks, and relevant source and built-runtime tests pass. Windows and POSIX results, filtered cases, skips, and unexecuted checks remain separately reported under the [testing policy](../../../../rsh/Docs/testing.md).
- Desktop and Python packaged runtimes launch from their relocated outputs. A command exit or successful archive creation alone is not runtime validation.
- The original development directory has a readable Git index and preserved user files. Recovery backups and remaining validation gaps are documented before final handoff; this note remains proposed until the migration is accepted.
