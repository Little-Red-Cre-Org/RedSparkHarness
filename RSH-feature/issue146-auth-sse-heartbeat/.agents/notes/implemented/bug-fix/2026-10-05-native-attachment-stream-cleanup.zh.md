# Agent Note：原生附件流清理

Status: implemented

[English](2026-10-05-native-attachment-stream-cleanup.md) | 中文

## 问题

原生附件 Provider 等待已打开的流，却丢弃清理失败结果，因此文件流关闭失败后，卸载仍可能报告成功。同步抛出的迭代器 return 错误也可能在已接纳操作排空前逃逸。批次中的准备失败还可能使门面操作提前结算，而其他已接纳准备任务仍在运行。

## 决策

[原生 Provider](../../../../rsh/Modules/Official/attachment/attachment-local/src/native.ts) 关闭接纳、取消读取，并等待已接纳操作及所有捕获的迭代器 return。调用者发起的迭代器 return 在实际完成之前保留所有权。只有流清理失败会拒绝共享关闭 Promise；单个失败保留错误身份，多个失败聚合报告。安装的取消监听器启动关闭，拥有的 disposer 报告同一 Promise 的结果。取消的图片调用者及时返回；既有按版本键索引的请求表通过后继任务保留每个被替换转换的完成状态，Provider 在关闭前等待这些转换和缓存写入。

## 考虑过的替代方案

首个 return 失败后立即拒绝，会让其他已接纳操作继续运行。把每个操作拒绝都视为清理失败，会误分类已经报告给调用者的请求失败。忽略所有结算失败则会隐藏未完成的清理。

## 后果

附件字节、引用、图片接纳和 Session 事件不变。旧版服务共享同一存储后端；本次变化仅涉及原生 Provider 关闭。

## 验证

既有批次用例验证另一项准备失败后，关闭仍等待被保持的准备任务，且不发布对象。既有暂停流用例同时检查抛出错误的迭代器 return、重复关闭的 Promise 身份，以及拒绝后续读取。既有共享转换取消用例验证替换任务可在已取消的前序任务仍被保持时完成，且 Provider 关闭会等待前序任务结算。无需新增测试用例或模型输出 fixture，因为附件输出不变；受影响的行为是关闭排空与清理错误报告。
