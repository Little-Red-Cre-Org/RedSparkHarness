## 2. 实现什么功能？

让模型在任务开始时只接收配置的基础工具和工具组目录。当模型发现需要编辑等能力时，申请对应工具组，下一次模型请求再得到该组工具。

例如，初始只有读取文件的 read 和申请工具组的 request_tool_group；editing 组包含 write、edit。用户提出“阅读 README 并补充启动说明”，模型先读取，再申请编辑组，下次请求获得编辑工具，随后按原有权限规则执行。

这里的“分阶段”是工具集合随着申请逐步扩大，不是系统自动把任务分类为规划、执行、验证等固定阶段。同一任务中开放状态累积，目前不自动收回。

## 4. 怎么打开这个功能？

### 只想先体验

直接打开上述 HTML 文件，无需配置模型、API Key 或安装插件。它用于体验规则，不会启用日常 RSH 中的功能。

### 在实际运行时启用

由维护 profile 的配置者完成以下接入。当前应在功能 worktree 对应的运行环境中操作；日常版本还没有部署此功能。

1. 先确认运行环境能够解析 `@deepseek-ai/dsh-tool-groups`。功能分支已添加 CLI 依赖。
2. 在同一 profile 作用域安装需要的工具，并确保 tools 与 activeSessions 服务可用。
3. 将下面的插件安装条目放在相关工具之后。
4. 在应用配置中设置 `builtinTools: false`，让受控工具通过统一注册表提供。
5. 重新加载该 profile，发起新任务；具体启动入口沿用所使用环境的既有启动方式。

```json
{
  "id": "tool-groups",
  "plugin": "@deepseek-ai/dsh-tool-groups",
  "scope": "root",
  "config": {
    "initial": ["read"],
    "groups": [
      {
        "name": "editing",
        "description": "创建或修改工作区文件",
        "tools": ["write", "edit"]
      }
    ]
  }
}
```

这是一条安装配置，不是完整 profile 文件；`builtinTools: false` 属于应用配置，不放入上面的插件 config 中。需要根据实际 profile 结构添加，不能直接覆盖整个配置文件。

工具名必须真实存在。未列入 initial 或 groups 的普通工具保持隐藏。request_tool_group 始终可用；若已安装 run_code，它作为传输入口始终可用，但其内部工具绑定仍按当前集合过滤。工具可见性不会把本来不受限制的终端变成只读环境。

## 5. 普通用户怎么使用？

用户只需照常输入需求，例如：

> 帮我阅读 README，并在文末补充启动说明。

预期流程：

1. 模型使用初始读取工具了解文件。
2. 模型根据工具组目录申请 editing。
3. 申请结果返回编辑工具参数说明；当前批次仍不能编辑。
4. 下一次模型请求获得 write、edit。
5. 实际编辑继续经过原有 guard、审批与沙箱检查；若既有规则要求用户确认，按既有流程处理。

用户不必手动输入工具名或切换阶段。实际模型是否主动申请、申请时机是否合理，还需要在启用后的真实使用中观察；离线测试验证的是机制，不代表所有模型都会表现一致。

## 6. 测试页怎么验收？

| 操作 | 应看到的结果 |
| --- | --- |
| 新任务直接点“尝试编辑” | 拦截：edit 未开放 |
| 申请编辑组后，仍在当前轮尝试编辑 | 继续拦截，状态显示等待下一轮 |
| 点击“进入下一次模型请求”，再尝试编辑 | 工具开放；允许写入时显示模拟成功 |
| 取消“允许写入”，再次尝试编辑 | 权限拒绝，工具开放不绕过权限 |
| 申请后模拟恢复当前任务 | 新请求恢复已申请的编辑组 |
| 点击“新建任务 / 重置” | 仅剩初始工具，不继承上一任务开放状态 |

这些是人工体验步骤，不替代真实运行时测试。
